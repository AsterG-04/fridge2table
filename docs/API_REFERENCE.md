# Fridge2Table — Backend API Reference

Base URL: local dev `http://127.0.0.1:8000` (or `http://10.0.2.2:8000` from an Android emulator); production `https://fridge2table-backend.onrender.com` (used automatically by release builds — see `frontend/fridge2table_app/lib/config/api_config.dart`).

All routes are defined in `backend/app/routes/inventory.py` and registered via `backend/app/main.py`. Interactive Swagger docs are auto-generated by FastAPI at `/docs` on any running instance.

**Auth model:** there is no token-based authentication on the backend itself. Every endpoint (except the root health check) requires a `user_id` query parameter — the caller is trusted to supply the correct, currently-signed-in Supabase user's UUID (the Flutter app always does, via `ApiService._userId`, which reads it from the live Supabase session and throws before making the request if nobody's signed in). **This means the backend itself does not verify that the caller is who they claim to be** — anyone who can reach the backend and knows/guesses a valid `user_id` could read or modify that user's pantry. This is a real security limitation worth naming explicitly in a report, not glossed over — CORS is fully open (`allow_origins=["*"]`) and there's no server-side JWT verification anywhere in `backend/app/`.

## `GET /`

**Purpose:** Health check.
**Auth:** None required.
**Query params:** None.
**Response:** `200 OK`
```json
{ "message": "F2T Backend Running" }
```

## `GET /inventory`

**Purpose:** List every ingredient belonging to `user_id`.
**Auth:** `user_id` query param (required).
**Query params:**
| Name | Type | Required | Description |
|---|---|---|---|
| `user_id` | string | Yes | Supabase user UUID |

**Response:** `200 OK`, array of `IngredientResponse`:
```json
[
  {
    "id": 1,
    "name": "Milk",
    "quantity": 1.0,
    "unit": "L",
    "expiry_date": "2026-08-02",
    "category": "Dairy",
    "location": "Fridge",
    "updated_at": "2026-07-29T10:15:00+00:00"
  }
]
```

**Example request:**
```
GET /inventory?user_id=85a91912-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

## `POST /ingredient`

**Purpose:** Create a new ingredient.
**Auth:** `user_id` query param (required).
**Query params:** `user_id` (string, required).
**Request body:** `IngredientCreate`
| Field | Type | Required | Notes |
|---|---|---|---|
| `name` | string | Yes | |
| `quantity` | float | Yes | |
| `unit` | string | Yes | |
| `expiry_date` | string \| null | No | `YYYY-MM-DD` |
| `category` | string \| null | No | |
| `location` | string \| null | No | |

**Example request:**
```
POST /ingredient?user_id=85a91912-xxxx-xxxx-xxxx-xxxxxxxxxxxx
Content-Type: application/json

{
  "name": "Apple",
  "quantity": 4,
  "unit": "pcs",
  "expiry_date": "2026-08-05",
  "category": "Fruits",
  "location": "Counter"
}
```

**Response:** `200 OK`, the created `IngredientResponse` (includes the database-assigned `id` and `updated_at`).

## `PUT /ingredient/{ingredient_id}`

**Purpose:** Update an existing ingredient (full replace of the editable fields — there is no partial-patch variant).
**Auth:** `user_id` query param (required) — the update only applies if the row's `user_id` matches; otherwise treated as not found.
**Path params:** `ingredient_id` (int).
**Query params:** `user_id` (string, required).
**Request body:** Same shape as `POST /ingredient` (`IngredientCreate`).
**Response:**
- `200 OK` — updated `IngredientResponse`.
- `404 Not Found` — `{"detail": "Ingredient not found"}` if no row with that id exists for that user.

---

## `DELETE /ingredient/{ingredient_id}`

**Purpose:** Delete an ingredient.
**Auth:** `user_id` query param (required), same ownership check as `PUT`.
**Path params:** `ingredient_id` (int).
**Query params:** `user_id` (string, required).
**Response:**
- `200 OK` — `{"message": "Ingredient deleted"}`.
- `404 Not Found` — `{"detail": "Ingredient not found"}`.

**Note:** this endpoint only deletes from the backend's own `pantry_items` table. The frontend (`ApiService.deleteIngredient()`) separately and additionally mirrors the delete to Supabase's cloud-sync table using a tombstone mechanism — the backend itself has no knowledge of or connection to that table (see `docs/DATABASE_SCHEMA.md`).

## `GET /expiry-status`

**Purpose:** Return every ingredient with a computed freshness `status`, re-derived fresh on every call (not stored anywhere).
**Auth:** `user_id` query param (required).
**Query params:** `user_id` (string, required).
**Status values:** `"expired"` (days left < 0), `"today"` (days left == 0), `"soon"` (1–3 days left), `"fresh"` (4+ days left), `"unknown"` (no `expiry_date`, or unparseable).
**Response:** `200 OK`
```json
[
  {
    "id": 1,
    "name": "Milk",
    "quantity": 1.0,
    "unit": "L",
    "category": "Dairy",
    "expiry_date": "2026-07-29",
    "status": "today"
  }
]
```

## `GET /recipes`

**Purpose:** Return recipes matched against the user's full current pantry (every item, regardless of freshness), annotated with expiry-warning fields.
**Auth:** `user_id` query param (required).
**Query params:** `user_id` (string, required).
**Matching rules** (see `docs/ARCHITECTURE.md` §4 for the full flow):
- Ingredient names normalized (lowercase, de-pluralized, synonym-mapped) before comparison.
- `match_score = round(matched_count / recipe_total_ingredients * 100)`.
- A candidate passes only if `match_score >= 20` **and** `matched_count >= min_match_count`, where `min_match_count` is `1` if the pantry has fewer than 5 distinct ingredients, else `2`.
- Results sorted by `match_score` descending, capped at 25.

**Response:** `200 OK`, array of full recipe objects (every field from `recipes_full.json` — `name`, `ingredients`, `steps`, `prep_time`, `cook_time`, `difficulty`, `nutrition`, `sustainability_tip`, `diet_tags`, `cuisine`, `id`) **plus**:
| Added field | Type | Description |
|---|---|---|
| `match_score` | int | 0–100 |
| `matched_ingredients` | string[] | Normalized names of the pantry ingredients that matched this recipe |
| `expired_ingredients` | string[] | Subset of `matched_ingredients` currently expired in the pantry |
| `expiring_ingredients` | string[] | Subset of `matched_ingredients` expiring today or within 3 days |

**Example response item:**
```json
{
  "id": 42,
  "name": "Aloo Gobi",
  "ingredients": ["potato", "cauliflower", "onion", "garlic", "turmeric"],
  "steps": ["...", "..."],
  "prep_time": "10 min",
  "cook_time": "25 min",
  "difficulty": "Easy",
  "nutrition": { "calories": 220, "protein": "5g", "carbs": "32g", "fat": "8g" },
  "sustainability_tip": "...",
  "diet_tags": ["Vegan", "Vegetarian", "Gluten-Free"],
  "cuisine": "Indian",
  "match_score": 20,
  "matched_ingredients": ["cauliflower"],
  "expired_ingredients": [],
  "expiring_ingredients": ["cauliflower"]
}
```

## `GET /ai-recommendation`

**Purpose:** Return a single "best pick" recipe name — LLM-assisted if configured, otherwise a deterministic fallback.
**Auth:** `user_id` query param (required).
**Query params:** `user_id` (string, required).
**Behavior:**
1. Runs the same matching as `/recipes` internally (not a separate dataset).
2. Filters to candidates that use an ingredient expiring today or soon, if any exist; otherwise uses the full candidate list. Takes the top 10.
3. If the backend has `OPENROUTER_API_KEY` set: sends the pantry + candidate names to `meta-llama/llama-3.3-70b-instruct:free` via OpenRouter, asking it to pick one by name. The reply is matched back against the candidate list case-insensitively (never trusted verbatim).
4. If no API key, the LLM call fails, times out (10s), or its reply doesn't match any candidate name: falls back to the single highest-`match_score` candidate.

**Response:** `200 OK`
```json
{ "recipe_name": "Aloo Gobi", "source": "ai" }
```
`source` is one of: `"ai"` (LLM picked it), `"fallback"` (deterministic top match, for any reason above), `"none"` (no candidates matched at all — `recipe_name` is `null` in this case).

## Error Handling Summary (all endpoints)

- Malformed/missing required fields in a request body → FastAPI's own `422 Unprocessable Entity` (Pydantic validation), not custom-handled.
- Missing `user_id` query param → `422 Unprocessable Entity` (FastAPI treats it as a required, unvalidated param).
- No matching row for `PUT`/`DELETE` → `404 Not Found` with a `detail` message.
- Uncaught server-side exceptions (e.g. a database connectivity issue) → FastAPI's default `500 Internal Server Error`, no custom error body — this is exactly the failure mode that caused the production "ingredient save failing" bug documented in `docs/PROJECT_OVERVIEW.md` §4 (commit `04f13a0`).
