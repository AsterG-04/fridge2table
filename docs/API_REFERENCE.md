# Fridge2Table — Backend API Reference

Base URL: local dev `http://127.0.0.1:8000` (or `http://10.0.2.2:8000` from an Android emulator); production `https://fridge2table-backend.onrender.com` (used automatically by release builds — see `frontend/fridge2table_app/lib/config/api_config.dart`).

All routes are defined in `backend/app/routes/inventory.py` and registered via `backend/app/main.py`. Interactive Swagger docs are auto-generated by FastAPI at `/docs` on any running instance.

**Auth model:** every protected endpoint requires an `Authorization: Bearer <supabase-jwt>` header. The backend verifies the token with Supabase's public JWKS endpoint using ES256 and uses the token's `sub` claim as the authenticated user id. The client-supplied `user_id` query parameter is no longer accepted anywhere; requests without a valid token receive `401 Unauthorized`.

## `GET /`

**Purpose:** Health check.
**Auth:** None required.
**Response:** `200 OK`
```json
{ "message": "F2T Backend Running" }
```

## `GET /inventory`

**Purpose:** List every ingredient belonging to the authenticated user.
**Auth:** `Authorization: Bearer <token>` required.
**Response:** `200 OK`, array of `IngredientResponse`.
```json
[
  {
    "id": 1,
    "name": "Milk",
    "quantity": 1.0,
    "unit": "L",
    "expiry_date": "2026-08-02",
    "category": "Dairy",
    "location": "Fridge",
    "updated_at": "2026-07-29T10:15:00+00:00"
  }
]
```

**Example request:**
```http
GET /inventory
Authorization: Bearer <supabase-access-token>
```

## `POST /ingredient`

**Purpose:** Create a new ingredient for the authenticated user.
**Auth:** `Authorization: Bearer <token>` required.
**Request body:** `IngredientCreate`

| Field | Type | Required | Notes |
|---|---|---|---|
| `name` | string | Yes | |
| `quantity` | float | Yes | |
| `unit` | string | Yes | |
| `expiry_date` | string \| null | No | `YYYY-MM-DD` |
| `category` | string \| null | No | |
| `location` | string \| null | No | |

**Example request:**
```http
POST /ingredient
Authorization: Bearer <supabase-access-token>
Content-Type: application/json

{
  "name": "Apple",
  "quantity": 4,
  "unit": "pcs",
  "expiry_date": "2026-08-05",
  "category": "Fruits",
  "location": "Counter"
}
```

**Response:** `200 OK`, the created `IngredientResponse` (includes the database-assigned `id` and `updated_at`).

## `PUT /ingredient/{ingredient_id}`

**Purpose:** Update an existing ingredient for the authenticated user.
**Auth:** `Authorization: Bearer <token>` required.
**Path params:** `ingredient_id` (int).
**Request body:** Same shape as `POST /ingredient` (`IngredientCreate`).
**Response:**
- `200 OK` — updated `IngredientResponse`.
- `404 Not Found` — `{"detail": "Ingredient not found"}` if no row with that id exists for that user.

---

## `DELETE /ingredient/{ingredient_id}`

**Purpose:** Delete an ingredient for the authenticated user.
**Auth:** `Authorization: Bearer <token>` required.
**Path params:** `ingredient_id` (int).
**Response:**
- `200 OK` — `{"message": "Ingredient deleted"}`.
- `404 Not Found` — `{"detail": "Ingredient not found"}`.

**Note:** this endpoint only deletes from the backend's own `pantry_items` table. The frontend also mirrors the delete to Supabase's cloud-sync table using a tombstone mechanism — the backend itself has no direct connection to that table (see `docs/DATABASE_SCHEMA.md`).

## `GET /expiry-status`

**Purpose:** Return every ingredient with a computed freshness `status`, re-derived fresh on every call.
**Auth:** `Authorization: Bearer <token>` required.
**Status values:** `"expired"` (days left < 0), `"today"` (days left == 0), `"soon"` (1–3 days left), `"fresh"` (4+ days left), `"unknown"` (no `expiry_date`, or unparseable).
**Response:** `200 OK`
```json
[
  {
    "id": 1,
    "name": "Milk",
    "quantity": 1.0,
    "unit": "L",
    "category": "Dairy",
    "expiry_date": "2026-07-29",
    "status": "today"
  }
]
```

## `GET /recipes`

**Purpose:** Return recipes matched against the authenticated user's current pantry, annotated with expiry-warning fields.
**Auth:** `Authorization: Bearer <token>` required.
**Matching rules** (see `docs/ARCHITECTURE.md` §4 for the full flow):
- Ingredient names are normalized (lowercase, de-pluralized, synonym-mapped) before comparison.
- `match_score = round(matched_count / recipe_total_ingredients * 100)`.
- A candidate passes only if `match_score >= 20` **and** `matched_count >= min_match_count`, where `min_match_count` is `1` if the pantry has fewer than 5 distinct ingredients, else `2`.
- Results are sorted by `match_score` descending and capped at 25.

**Response:** `200 OK`, an array of full recipe objects plus these extra fields:

| Added field | Type | Description |
|---|---|---|
| `match_score` | int | 0–100 |
| `matched_ingredients` | string[] | Normalized names of the pantry ingredients that matched this recipe |
| `expired_ingredients` | string[] | Subset of `matched_ingredients` currently expired in the pantry |
| `expiring_ingredients` | string[] | Subset of `matched_ingredients` expiring today or within 3 days |

**Example response item:**
```json
{
  "id": 42,
  "name": "Aloo Gobi",
  "ingredients": ["potato", "cauliflower", "onion", "garlic", "turmeric"],
  "steps": ["...", "..."],
  "prep_time": "10 min",
  "cook_time": "25 min",
  "difficulty": "Easy",
  "nutrition": { "calories": 220, "protein": "5g", "carbs": "32g", "fat": "8g" },
  "sustainability_tip": "...",
  "diet_tags": ["Vegan", "Vegetarian", "Gluten-Free"],
  "cuisine": "Indian",
  "match_score": 20,
  "matched_ingredients": ["cauliflower"],
  "expired_ingredients": [],
  "expiring_ingredients": ["cauliflower"]
}
```

## `GET /ai-recommendation`

**Purpose:** Return a single "best pick" recipe name — LLM-assisted if configured, otherwise a deterministic fallback.
**Auth:** `Authorization: Bearer <token>` required.
**Behavior:**
1. Runs the same matching as `/recipes` internally.
2. Filters to candidates that use an ingredient expiring today or soon, if any exist; otherwise uses the full candidate list and takes the top 10.
3. If `OPENROUTER_API_KEY` is set, the backend sends the pantry and candidate names to OpenRouter and uses the model's pick if it matches a known recipe name.
4. If the LLM call is unavailable or returns no usable match, the backend falls back to the highest-`match_score` candidate.

**Response:** `200 OK`
```json
{ "recipe_name": "Aloo Gobi", "source": "ai" }
```
`source` is one of: `"ai"` (LLM picked it), `"fallback"` (deterministic top match), or `"none"` (no candidates matched at all — `recipe_name` is `null` in this case).

## Error Handling Summary (all endpoints)

- Missing or malformed `Authorization` header → `401 Unauthorized`.
- Invalid or expired JWT → `401 Unauthorized`.
- Missing required request fields → FastAPI's `422 Unprocessable Entity`.
- No matching row for `PUT`/`DELETE` → `404 Not Found` with a `detail` message.
- Uncaught server-side exceptions → FastAPI's default `500 Internal Server Error`.
