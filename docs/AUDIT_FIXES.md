# Audit Fixes

This documents the fixes applied for the gaps identified during the earlier documentation audit (see `PROJECT_OVERVIEW.md` §6, `API_REFERENCE.md`'s auth note, and `DATA_PERSISTENCE.md`'s opening note) — what changed, what was deliberately left alone, and the one manual setup step still needed from whoever holds the Supabase/Render dashboards.

## Fixed

**1. Push notifications never fired.** `NotificationService` is now wired up end to end: `main.dart` initializes the notification channel at app startup and requests OS permission right after every sign-in/sign-up completion path (email/password, Google OAuth, and post-onboarding). `checkAndNotify()` fires on Home load, on every inventory refresh, and on app resume (`WidgetsBindingObserver`) — capped at one notification per ingredient per calendar day via a `SharedPreferences`-backed history (`notification_service.dart`), and gated by the new Settings "Push Notifications" toggle (see #6 below).

**2. Privacy Policy claimed pantry data was stored on-device by default.** It never was — the backend has always been a hosted FastAPI service on Render, backed by Supabase Postgres, for every deployed build. `privacy_screen.dart` now says plainly: account data lives in Supabase Auth, pantry data lives on the FastAPI/Postgres backend scoped to your account, and camera photos are processed entirely on-device via the TFLite classifier and never uploaded — this last claim was re-verified against `ingredient_classifier_service.dart` and the camera screens before writing it (no network call anywhere in that path). The "Your control over your data" section was also corrected to describe the real Clear Data / account-deletion behavior instead of a nonexistent local-clear mechanism.

**3. "Cloud Sync" implied multi-device sync that the feature doesn't actually provide.** Multi-device access already works for free because the backend itself is centrally hosted — the screen actually mirrors data into a secondary Supabase table as a backup. Renamed to "Backup & Restore" throughout (screen title, Profile and Settings menu entries), reworded messaging ("back up your pantry" instead of "sync across devices"), "Sync Now" → "Back Up Now", and the three toggles (now "Auto Backup on WiFi" / "Auto Backup on Mobile Data" / "Background Backup") are wired to real behavior via `AppSettingsService` + `connectivity_plus`: WiFi/mobile-data toggles gate an automatic backup on app launch (`SupabaseService.autoBackupIfAllowed()`, called from `MainScreen.initState()`), and Background Backup drives a 15-minute periodic timer while the app is open. The old hardcoded "Local Database ... 2.4 MB" card (a fictional figure) was replaced with real, live item counts for both the primary backend and the backup copy.

**4. Dead code.** `lib/models/recipe.dart` (superseded by `RecipeDetail`) had zero references anywhere in the codebase and has been deleted, per your confirmation. A repo-wide audit checked every other file in `lib/models`, `lib/services`, `lib/screens`, `lib/data`, `lib/widgets`, plus the entire backend (unused imports, unwired routes, dead `crud.py` functions, commented-out code) — everything else is actively referenced. One unrelated item surfaced during the sweep: `backend/run.py` has been a 0-byte file since the very first commit — not part of this cleanup (out of scope, and not clearly a mistake vs. an intentional placeholder), flagging here in case it's worth a look separately.

**5. UI-only placeholders.**
- *Notification Settings toggle* — now backed by `AppSettingsService` (`SharedPreferences`, default on); `checkAndNotify()` returns early when off.
- *Dark Mode toggle* — no longer silently flips state; tapping it shows "Dark mode is coming in a future update. Stay tuned!" and the toggle itself stays off.
- *Forgot Password* — wired to `supabase.auth.resetPasswordForEmail()` via a real email-entry dialog, with a success message and friendly error handling (bad email, network failure, etc).
- *Help & Support* — real dialog with the contact email (`fridge2table.support@example.com` — placeholder, swap for a real address later) and a working "Copy Email" clipboard button.
- *Cooking Timer* — recipes can now carry an optional `step_timers` field (list of nullable minute-counts, positional with `steps`); four illustrative recipes were annotated (Margherita Pizza, Baked Salmon with Vegetables, Tomato Soup, Baked Sweet Potato) via `generate_recipes.py`, the rest are unaffected (field absent = no timer). Steps with a duration show a prominent countdown with Start/Pause/Reset; on reaching zero it plays a system alert sound, vibrates, and shows "Timer done! Move to next step."

**6. No server-side request authentication.** Every backend endpoint (except the health check) previously trusted whatever `user_id` query parameter was sent — anyone who knew or guessed another user's id could read or write their pantry. Fixed with a proper FastAPI dependency (`backend/app/auth.py`, `get_current_user_id`): it extracts the `Authorization: Bearer <token>` header, verifies the JWT against `SUPABASE_JWT_SECRET` (HS256), and returns the token's `sub` claim as the authenticated user id — the query parameter is no longer read at all. Requests without a valid token get a `401`. The frontend (`api_service.dart`) now attaches `Authorization: Bearer <session-access-token>` on every call and, on any `401` response, signs out, clears the local session, and drops the user back on the Sign In screen. **Verified locally**: a request with no/garbage token gets `401`; a validly-signed token is accepted regardless of what `user_id` is in the query string (proving the query param really is ignored now); the health check (`GET /`) stays open with no token required.

## Manual setup you still need to do: `SUPABASE_JWT_SECRET`

The backend fails closed until this is set — every request will `401`, including from the app itself, until it's added to Render.

1. **Find the secret in Supabase:** open your project at [supabase.com](https://supabase.com/dashboard), go to **Project Settings → Data API** (older dashboards: **Settings → API**), and look for the **JWT Keys** / **JWT Settings** section.
   - If you see a field literally labeled **"JWT Secret"** — a long random string — that's the value you need.
   - **Possible snag:** this project's anon key already uses Supabase's newer `sb_publishable_...` format, which usually means the project may have been provisioned under Supabase's newer *JWT Signing Keys* system (asymmetric ES256/RS256 keys, verified via a JWKS endpoint) instead of the older shared-secret one. If that section shows **"JWT Signing Keys"** with an algorithm and no plain secret string to copy, **stop and tell me** — the verification code in `backend/app/auth.py` currently assumes the classic shared-secret (HS256) approach, and would need a different implementation (fetching Supabase's public JWKS instead of a shared secret) for that case.
2. **Add it to Render:** in the Render dashboard, open the `fridge2table-backend` service → **Environment** tab → **Add Environment Variable** → Key `SUPABASE_JWT_SECRET`, Value: paste the secret from step 1 → **Save Changes**. This triggers an automatic redeploy.
3. **Test it after the deploy finishes:**
   ```
   curl -i https://fridge2table-backend.onrender.com/inventory?user_id=anything
   ```
   should return `401 Unauthorized` (proving the query param alone no longer gets you in). Then open the rebuilt app and sign in normally — if sign-in and the Home screen load pantry data as usual, real session tokens are being accepted correctly. If instead every screen immediately bounces back to Sign In after loading, the secret value doesn't match what Supabase is actually signing tokens with — most likely because of the JWT Signing Keys situation in step 1.
