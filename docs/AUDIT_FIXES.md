# Audit Fixes

This documents the fixes applied for the gaps identified during the earlier documentation audit (see `PROJECT_OVERVIEW.md` §6, `API_REFERENCE.md`'s auth note, and `DATA_PERSISTENCE.md`'s opening note) — what changed, what was deliberately left alone, and a follow-up correction to the JWT verification approach made after real-world testing.

## Fixed

**1. Push notifications never fired.** `NotificationService` is now wired up end to end: `main.dart` initializes the notification channel at app startup and requests OS permission right after every sign-in/sign-up completion path (email/password, Google OAuth, and post-onboarding). `checkAndNotify()` fires on Home load, on every inventory refresh, and on app resume (`WidgetsBindingObserver`) — capped at one notification per ingredient per calendar day via a `SharedPreferences`-backed history (`notification_service.dart`), and gated by the new Settings "Push Notifications" toggle (see #6 below).

**2. Privacy Policy claimed pantry data was stored on-device by default.** It never was — the backend has always been a hosted FastAPI service on Render, backed by Supabase Postgres, for every deployed build. `privacy_screen.dart` now says plainly: account data lives in Supabase Auth, pantry data lives on the FastAPI/Postgres backend scoped to your account, and camera photos are processed entirely on-device via the TFLite classifier and never uploaded — this last claim was re-verified against `ingredient_classifier_service.dart` and the camera screens before writing it (no network call anywhere in that path). The "Your control over your data" section was also corrected to describe the real Clear Data / account-deletion behavior instead of a nonexistent local-clear mechanism.

**3. "Cloud Sync" implied multi-device sync that the feature doesn't actually provide.** Multi-device access already works for free because the backend itself is centrally hosted — the screen actually mirrors data into a secondary Supabase table as a backup. Renamed to "Backup & Restore" throughout (screen title, Profile and Settings menu entries), reworded messaging ("back up your pantry" instead of "sync across devices"), "Sync Now" → "Back Up Now", and the three toggles (now "Auto Backup on WiFi" / "Auto Backup on Mobile Data" / "Background Backup") are wired to real behavior via `AppSettingsService` + `connectivity_plus`: WiFi/mobile-data toggles gate an automatic backup on app launch (`SupabaseService.autoBackupIfAllowed()`, called from `MainScreen.initState()`), and Background Backup drives a 15-minute periodic timer while the app is open. The old hardcoded "Local Database ... 2.4 MB" card (a fictional figure) was replaced with real, live item counts for both the primary backend and the backup copy.

**4. Dead code.** `lib/models/recipe.dart` (superseded by `RecipeDetail`) had zero references anywhere in the codebase and has been deleted, per your confirmation. A repo-wide audit checked every other file in `lib/models`, `lib/services`, `lib/screens`, `lib/data`, `lib/widgets`, plus the entire backend (unused imports, unwired routes, dead `crud.py` functions, commented-out code) — everything else is actively referenced. One unrelated item surfaced during the sweep: `backend/run.py` has been a 0-byte file since the very first commit — not part of this cleanup (out of scope, and not clearly a mistake vs. an intentional placeholder), flagging here in case it's worth a look separately.

**5. UI-only placeholders.**
- *Notification Settings toggle* — now backed by `AppSettingsService` (`SharedPreferences`, default on); `checkAndNotify()` returns early when off.
- *Dark Mode toggle* — no longer silently flips state; tapping it shows "Dark mode is coming in a future update. Stay tuned!" and the toggle itself stays off.
- *Forgot Password* — wired to `supabase.auth.resetPasswordForEmail()` via a real email-entry dialog, with a success message and friendly error handling (bad email, network failure, etc).
- *Help & Support* — real dialog with the contact email (`fridge2table.support@example.com` — placeholder, swap for a real address later) and a working "Copy Email" clipboard button.
- *Cooking Timer* — recipes can now carry an optional `step_timers` field (list of nullable minute-counts, positional with `steps`). Originally only four illustrative recipes were annotated by hand; `backend/scripts/backfill_step_timers.py` (added later — see `docs/ARCHITECTURE.md`) closed the resulting near-total coverage gap by extracting explicit durations ("bake for 15-18 minutes", "1.5-2 hours") straight out of each recipe's own step text via regex, taking coverage from 4/302 to 93/302 recipes (99 individual steps). The countdown UI itself (`CookingModeScreen`) was never the problem — it always correctly showed a prompt with Start/Pause/Reset for any step that *had* a duration and played a system alert sound + vibrated + showed "Timer done! Move to next step." on reaching zero; it just had almost no data to work with.

**6. No server-side request authentication.** Every backend endpoint (except the health check) previously trusted whatever `user_id` query parameter was sent — anyone who knew or guessed another user's id could read or write their pantry. Fixed with a proper FastAPI dependency (`backend/app/auth.py`, `get_current_user_id`) that extracts the `Authorization: Bearer <token>` header, verifies it, and returns the token's `sub` claim as the authenticated user id — the query parameter is no longer read at all. Requests without a valid token get a `401`. The frontend (`api_service.dart`) attaches `Authorization: Bearer <session-access-token>` on every call and, on any `401` response, signs out, clears the local session, and drops the user back on the Sign In screen.

## Follow-up: JWT verification algorithm (ES256, not HS256)

The first version of #6 above verified tokens with a shared secret (`SUPABASE_JWT_SECRET`, HS256) — the classic Supabase approach, and what was originally requested. Real-world testing surfaced two problems, both now fixed:

- **The local dev backend never had `SUPABASE_JWT_SECRET` set at all** (`backend/.env` only had `OPENROUTER_API_KEY`), so it 401'd every request unconditionally. This was flagged when testing against the local backend produced the same "must be signed in" symptom as production — which at the time looked like it ruled out a JWT-secret problem, but was actually the same class of problem via a different gap (missing entirely, rather than mismatched).
- **This Supabase project signs tokens with ES256** (asymmetric, elliptic curve), not HS256 — confirmed by decoding a real session token's header (`"alg": "ES256"`) and cross-checking the project's own JWKS endpoint (`https://xdwlhmuhqsndkimejlvi.supabase.co/auth/v1/.well-known/jwks.json`), which serves exactly one ES256/P-256 key. This is exactly the ambiguity flagged in the original version of this section: the project's `sb_publishable_...`-format anon key was the tell that it uses Supabase's newer JWT Signing Keys system. A shared secret can never verify an asymmetric signature — every request was rejected as invalid regardless of how fresh or genuinely valid the token was.

**The fix** (`backend/app/auth.py`, `backend/app/config.py`): verification now uses `PyJWT`'s `PyJWKClient` to fetch Supabase's public key set from its JWKS endpoint, cached in-process for an hour (`cache_keys=True, lifespan=3600`) so it isn't refetched on every request, with automatic refetch on a cache miss (e.g. after Supabase rotates its signing key). `SUPABASE_JWT_SECRET` is gone entirely — there is nothing to set in Render for this anymore. The JWKS URL is derived from `SUPABASE_URL` (defaults to this project's URL, matching what the frontend already embeds in `supabase_config.dart` — not sensitive, no env var required, though one exists as an override for a different project).

**Verified locally**: no/garbage tokens get `401`; a token signed with the *wrong* key but carrying the *real* key's `kid` in its header correctly gets looked up and then rejected ("Signature verification failed"), proving the JWKS-fetch-and-key-selection path works end to end; the health check (`GET /`) stays open with no token required. A token genuinely signed by Supabase's real private key couldn't be tested from this environment (no access to real user credentials) — confirm this works by signing into the rebuilt app and checking that Home/Recipes load pantry data normally rather than bouncing back to Sign In.

**If you already added `SUPABASE_JWT_SECRET` to Render:** it's safe to delete — the code no longer reads it.
