# Fridge2Table — Codebase Guide

Every source file in the project, what it does, its key classes/functions, and how it connects to the rest of the codebase. Organized by directory, matching the actual repo layout.

---

## Backend — `backend/`

### `app/main.py`
FastAPI application entry point. Calls `Base.metadata.create_all(bind=engine)` to ensure tables exist, configures fully-open CORS (`allow_origins=["*"]` — no browser-origin restriction needed since this is a native mobile client with no cookie-based auth), includes the single router from `routes/inventory.py`, and defines the root health-check endpoint (`GET /` → `{"message": "F2T Backend Running"}`). This is the file Uvicorn is pointed at (`uvicorn app.main:app`).

### `app/database.py`
Defines the SQLAlchemy `engine`, `SessionLocal` sessionmaker, and declarative `Base`. Reads `DATABASE_URL` from the environment (via `python-dotenv`'s `.env` loading); falls back to a local SQLite file (`sqlite:///./fridge2table.db`) if unset. Sets `check_same_thread: False` only for SQLite (a SQLite-specific connection quirk, not needed for Postgres).

### `app/models.py`
Single SQLAlchemy model, `Ingredient`, mapped to the `pantry_items` table (deliberately not named `ingredients` — see `docs/DATABASE_SCHEMA.md` for why). Columns: `id`, `name`, `quantity`, `unit`, `expiry_date`, `category`, `location`, `user_id`, `updated_at` (auto-set via a module-level `_utcnow()` helper on both insert and update).

### `app/schemas.py`
Pydantic request/response models. `IngredientCreate` (the request-body shape for both create and update). `IngredientResponse` extends it with `id` and `updated_at`, plus a `field_validator` that normalizes a timezone-naive `updated_at` (a SQLite round-trip quirk) to UTC before it's ever serialized, so every client sees a consistent, always-timezone-aware timestamp regardless of which database engine is behind the request.

### `app/crud.py`
Four plain functions wrapping SQLAlchemy queries, no classes: `create_ingredient()`, `get_ingredients()` (filtered by `user_id`), `update_ingredient()` (filtered by `id` **and** `user_id`, returns `None` if no match), `delete_ingredient()` (same ownership check, returns `None` if no match else a confirmation dict). Called exclusively from `routes/inventory.py`.

### `app/config.py`
Three module-level constants read from the environment: `OPENROUTER_API_KEY` (empty string if unset — the app is designed to work without it), `OPENROUTER_MODEL` (hardcoded to `"meta-llama/llama-3.3-70b-instruct:free"`), `OPENROUTER_URL`.

### `app/routes/inventory.py`
The **only** router in the app — every single API endpoint lives here (see `docs/API_REFERENCE.md` for the full endpoint list). Beyond the route handlers themselves, this file also contains:
- `_SYNONYMS` — a dict mapping AI-classifier/regional spelling variants to canonical recipe-dataset spellings (e.g. `"capsicum" -> "bell pepper"`).
- `_normalize()` — lowercases, de-pluralizes, and synonym-maps an ingredient name for matching purposes.
- A module-level load of `recipes_full.json` into `ALL_RECIPES` and a prebuilt `RECIPE_INDEX` (normalized ingredient name → list of recipe indices) — built **once** at import time, not per-request.
- `_expiry_status_for()` — the single source of truth for the expired/today/soon/fresh/unknown classification, used by both `/expiry-status` and the recipe-annotation logic in `/recipes`/`/ai-recommendation`.
- `_matched_recipes()` — the core matching algorithm (see `docs/ARCHITECTURE.md` §4).
- `_expiry_map()` — builds a normalized-name → worst-case-status lookup used to annotate `/recipes`' response with `expired_ingredients`/`expiring_ingredients`.

### `app/routes/__init__.py`
Empty — exists only to make `routes` a Python package.

### `data/recipes_full.json`
The recipe dataset itself, also bundled as a frontend asset (`frontend/fridge2table_app/assets/data/recipes_full.json`, a manually-kept-in-sync copy) so `LocalRecipeMatcher` can match recipes offline with no backend at all — see `docs/ARCHITECTURE.md` §7: `{"recipes": [...], "index": {...}}`. `"recipes"` is a flat array of 302 objects, each with `id`, `name`, `ingredients` (string array), `steps` (string array), `prep_time`, `cook_time`, `difficulty`, `nutrition` (`{calories, protein, carbs, fat}`), `sustainability_tip`, `diet_tags` (string array), `cuisine`, and an optional `step_timers` (integer-or-null array, positional with `steps` — a per-step countdown duration in minutes; 93 of the 302 recipes have this, via `backfill_step_timers.py`). `"index"` is a pre-built ingredient-name → recipe-index-array lookup, generated by `generate_recipes.py`'s own `build_index()` — **note this on-disk index is not actually the one used at runtime**; `routes/inventory.py` rebuilds its own `RECIPE_INDEX` from scratch at import time using its own `_normalize()` (which differs slightly from whatever normalization, if any, `generate_recipes.py` used when building the on-disk `"index"` key), so the on-disk index is effectively unused dead weight in the JSON file rather than something the backend actually reads.

### `scripts/generate_recipes.py`
A large, hand-authored Python script (not run automatically — a one-off content-generation tool). Contains the entire `RECIPES` list (302 dicts, one per recipe) as literal Python data, a `build_index()` helper, and a `main()` that assigns sequential `id`s, asserts every recipe has all required keys and there are at least 50 recipes, and writes the result to `data/recipes_full.json`. Its own docstring documents that this replaced an earlier, much thinner dataset derived from `cuisine_data.csv`/`recipes_index.json` (a cuisine-*classification* dataset with no real dish names) — those files are no longer part of the active dataset. Run manually: `venv/Scripts/python.exe scripts/generate_recipes.py`.

### `scripts/migrate_add_user_id.py`
A one-off, safe-to-rerun SQLite migration script (operates directly on `backend/fridge2table.db` via the `sqlite3` module, bypassing SQLAlchemy) that adds the `user_id` column to whatever table existed before per-user scoping. Skips itself if the column already exists. Only relevant to local SQLite dev history — the production Postgres database's equivalent migration was applied directly via Supabase's SQL Editor, not this script.

### `scripts/backfill_step_timers.py`
A one-off, safe-to-rerun content-generation script that mines each recipe's own step text for explicit durations ("bake for 15-18 minutes", "1.5-2 hours") via regex and writes the result into that recipe's `step_timers` field, in place, in `data/recipes_full.json` — closing a near-total data-coverage gap (originally only 4/302 recipes had any `step_timers` at all, so `CookingModeScreen`'s countdown UI, which was always correct, almost never had anything to show). A range's two bounds are averaged and rounded; hours convert to minutes first. Recipes that already have `step_timers` are left untouched, so it's safe to re-run after adding new recipes. Run: `venv/Scripts/python.exe scripts/backfill_step_timers.py`.

### `requirements.txt`
Pinned dependency versions: `fastapi`, `uvicorn`, `SQLAlchemy`, `pydantic`, `psycopg2-binary` (Postgres driver), `python-dotenv`, `httpx` (used for the OpenRouter call), plus their transitive dependencies.

## Frontend — `frontend/fridge2table_app/lib/`

### `main.dart`
App entry point (`void main()`) and the two top-level widgets:
- `Fridge2TableApp` (root `StatefulWidget`) — initializes `ApiConfig` and `SupabaseService` before `runApp()` (both genuinely block the first frame: `Fridge2TableApp.build()` synchronously checks `Supabase.instance.client.auth.currentSession`); `NotificationService.initialize()` is fired unawaited *after* `runApp()` instead, since nothing on the first screen needs it and it was previously adding an extra platform-channel round trip to the startup critical path for no benefit. Owns the root `onAuthStateChange` listener (`_handleSignedIn`, see `docs/ARCHITECTURE.md` §2), and decides `home:` (straight to `MainScreen` if a persisted session exists, else `SplashScreen`).
- `MainScreen` (`StatefulWidget`) — the bottom-nav shell. Holds a fixed `_screens` list (`HomeScreen`, `InventoryScreen`, `RecipeScreen`, `ProfileScreen`) and swaps between them via plain array indexing (`body: _screens[_currentIndex]`) — **not** an `IndexedStack`, so each tab's full widget/state tree is disposed and recreated on every switch, not preserved. Kicks off one silent background `SupabaseService.autoBackupIfAllowed()` call and starts a 15-minute background-backup timer in its own `initState()`; also holds a `connectivity_plus` listener (`_listenForReconnect`) that triggers `ApiService.getInventory()` on the offline→online transition to push any queued offline pantry edits (see `docs/ARCHITECTURE.md` §7). Renders `OfflineBanner` above the active tab and the custom bottom nav bar with the raised center scan button.

### `config/api_config.dart`
`ApiConfig` — resolves the backend's base URL once at startup (`initialize()`, awaited before `runApp()`), then exposes it as a plain synchronous `baseUrl` getter. Resolution priority: an explicit `--dart-define=API_BASE_URL` override, then release-build mode (always the deployed Render URL), then platform detection (web/non-Android → `localhost:8000`; Android emulator → `10.0.2.2:8000`; Android physical device → `localhost:8000`, relying on `adb reverse`). Also exposes `usingAdbReverse`, used by `ApiService` to give a precise error message when a physical dev device can't connect.

### `config/supabase_config.dart`
`SupabaseConfig` — three hardcoded constants (`url`, `anonKey`, `ingredientsTable = "ingredients"`), the OAuth deep-link redirect string, and an `isConfigured` getter (checks the constants aren't still the placeholder template values).

### `constants/colors.dart`
`AppColors` — nine named `Color` constants forming the app's palette (see `docs/UI.md` for the full design-token documentation, including where each is used).

### `data/allergy_severities.dart`
A single top-level constant, `allergySeverities` (`Map<String, String>`), mapping each of the 10 fixed allergy names to a severity label (`"Common"`/`"Moderate"`/`"Severe"`). Used by `ProfileScreen` to color-code the allergy summary card.

### `models/ingredient.dart`
`Ingredient` — the core pantry-item model. `toJson()` (for the backend, omits `id`/`updated_at`/`user_id` since the backend derives/ignores those on write), `fromJson()` (from either the backend or Supabase — both use the same field names), `toSupabaseJson(userId)` (adds `id`, `updated_at`, and the explicit `user_id`, since Supabase's table needs all three supplied by the client).

### `models/recipe.dart`
`Recipe` — a minimal, effectively dead class (`fromJson()` just calls `.toString()` on whatever's passed in). **Nothing in the app imports or instantiates it** (confirmed via a repo-wide search) — superseded by `RecipeDetail`. Kept here for documentation completeness, not because it's used.

### `models/recipe_detail.dart`
`RecipeDetail` (plus small companion classes `RecipeIngredientDetail`, `NutritionInfo`, `CookingStep`) — the model every recipe-related screen actually uses. `RecipeDetail.fromJson()` builds directly from the backend's `/recipes` response, including the `expiredIngredients`/`expiringIngredients` lists added for the freshness-warning banners. `RecipeDetail.forName()` is a deliberately minimal fallback constructor for places that only know a recipe's name (Cooked History's "Cook Again"), not its full data.

### `models/sync_result.dart`
`SyncResult` — a tiny plain result type (`success`, `message`, `syncedCount`) returned by every `SupabaseService` sync method, plus a `SyncResult.failure(message)` convenience factory.

### `models/ingredient_deduction.dart`
`IngredientDeduction` — represents one ingredient's outcome after a cook (before/after quantity labels, whether it was skipped or only symbolically "used" because it wasn't in the pantry, and the raw `amountUsed`/`unit` used to compute Recipe Complete's sustainability stats).

### `models/planned_ingredient_usage.dart`
`PlannedIngredientUsage` — the pre-deduction preview model used by `AdjustQuantitiesScreen` (name, initials, the matched pantry item or `null`, and the default amount to pre-fill).

### `models/cooked_history_entry.dart`
Two things in one file: `CookedHistoryEntry` (the persisted model — name, time, calories, timesCooked, lastCookedLabel, deductionSummary, ingredientNames) and `CookedHistoryStore` (the static store class — `load()`/`recordCook()`/`reset()`/persisted via `SharedPreferences`, plus derived getters: `totalMealsCooked`, `uniqueRecipes`, `totalCalories`, `totalFoodSavedKg`, `ecoScore` (8 points/meal, capped at 100), `badgeCount`, `categoryCounts` (keyword-matched against recipe ingredient names, same category vocabulary as the pantry screens)).

### `services/api_service.dart`
`ApiService` — the sole gateway to the FastAPI backend (see `docs/ARCHITECTURE.md` §9). Every method that touches the network goes through the private `_send()` wrapper for consistent timeout/error handling, which throws `NetworkUnavailableException` specifically for "couldn't reach the server at all" failures. The four pantry CRUD methods (`getInventory`/`addIngredient`/`updateIngredient`/`deleteIngredient`) catch that exception to fall back to/queue in `LocalPantryStore` — see `docs/ARCHITECTURE.md` §7. `getRecipesDetailed()`/`getAiRecommendation()` are also offline-aware (fall back to `LocalRecipeMatcher`, see below). `getExpiryStatus()` deliberately stays online-only. `getRecipes()` (names-only, legacy form) is unused dead code, confirmed via a repo-wide search — nothing calls it.

### `services/local_pantry_store.dart`
`LocalPantryStore` — the sqflite-backed local pantry cache and offline pending-write queue behind `ApiService`'s offline support (see `docs/ARCHITECTURE.md` §7, `docs/DATA_PERSISTENCE.md`). Not called by any screen directly.

### `services/local_recipe_matcher.dart`
`LocalRecipeMatcher` — a rule-for-rule Dart port of the backend's recipe-matching algorithm (`_normalize`, `_matched_recipes`, `_expiry_status_for`/`_expiry_map`, the same scoring/threshold constants), run against a bundled copy of `recipes_full.json` (`assets/data/recipes_full.json` — must be manually re-copied if the backend's dataset changes, no automated sync) instead of a live pantry query. Backs `ApiService.getRecipesDetailed()`/`getAiRecommendation()`'s offline fallback (see `docs/ARCHITECTURE.md` §7). Not called by any screen directly.

### `services/supabase_service.dart`
`SupabaseService` — the sole gateway to Supabase Auth session state and the cloud-sync table (see `docs/ARCHITECTURE.md` §8 and §6 for the full sync algorithm).

### `services/auth_service.dart`
`AuthService` — local cache of identity + non-sensitive preferences (see `docs/ARCHITECTURE.md` §8, `docs/DATA_PERSISTENCE.md` for exactly what survives what).

### `services/user_scope.dart`
`UserScope` — the per-user `SharedPreferences` key-namespacing helper every other local-storage service depends on (see `docs/DATABASE_SCHEMA.md` §4).

### `services/delete_tombstones.dart`
`DeleteTombstones` — the persisted per-user set of pending-cloud-delete ingredient ids (see `docs/ARCHITECTURE.md` §6).

### `services/secure_storage_service.dart`
Exposes the shared `secureStorage` (`FlutterSecureStorage`) instance, plus two adapter classes (`SecureSupabaseLocalStorage`, `SecureSupabasePkceStorage`) that the Supabase SDK is configured to use instead of its own `SharedPreferences`-backed defaults, so the session tokens and PKCE verifier land in secure storage.

### `services/saved_recipes_store.dart`
`SavedRecipesStore` — bookmarked-recipe-name persistence, structurally identical to `CookedHistoryStore`'s pattern (in-memory cache + `SharedPreferences`, per-user scoped, `reset()` on logout).

### `services/ingredient_classifier_service.dart`
`IngredientClassifierService` — loads the bundled TFLite model (`assets/models/ingredient_classifier_v4.tflite`) and class names (`class_names_v4.json`) once (memoized `initialize()`), and `classify(imagePath, topK)` runs on-device inference: decode → resize to 224×224 → build the input tensor → `interpreter.run()` → sort scores descending → return the top-K as `ClassificationResult(label, confidence)`.

### `services/recipe_cooking_service.dart`
`RecipeCookingService` — pure deduction logic, no state (see `docs/ARCHITECTURE.md` §8 and §5).

### `services/notification_service.dart`
`NotificationService` — fires one OS notification per expired/today/soon ingredient (`checkAndNotify()`, called from `HomeScreen.initState()` and on every app resume), capped at once per ingredient per calendar day via a `SharedPreferences`-backed history. `initialize()` sets up the Android notification channel and is safe to call repeatedly (idempotent past the first real call); `checkAndNotify()`/`requestPermission()` both call it themselves before touching the plugin, so callers never need to remember to.

### `widgets/async_state.dart`
`AsyncStateBuilder<T>` — the one shared widget in the whole app, used by most `FutureBuilder`-driven screens. Cleanly separates four states so a screen never gets stuck showing a spinner indefinitely: loading (`ConnectionState.waiting`), error (retry button + the translated error message), genuinely empty data (a configurable icon/title/subtitle "nothing here" state, via the optional `isEmpty` callback), and real data (delegates to the caller's `builder`).

### `widgets/offline_banner.dart`
`OfflineBanner` — a `StreamBuilder` over `Connectivity().onConnectivityChanged` that renders a thin "You're offline — changes will sync when you're back online" strip when there's no network path at all, `SizedBox.shrink()` otherwise. Purely a passive indicator (has no effect on whether syncing actually happens — that's `MainScreen`'s connectivity listener, see `main.dart` above). Also exports `isOfflineResult()`, reused by `RecipeScreen`'s own small offline note (recipes work offline now — see `LocalRecipeMatcher` below — so this is just "here's why", not a block).

## Frontend Screens — `lib/screens/` (25 files)

Grouped by area, each with: purpose, what it displays, key service calls, what it navigates to/from.

### Onboarding & Auth

- **`signin_screen.dart`** — Email/password sign-in + Google OAuth entry point. Calls `Supabase.instance.client.auth.signInWithPassword()`/`signInWithOAuth()`, `AuthService.cacheIdentity()`, `SupabaseService.resolveConflicts()`. Navigates to `MainScreen` (success) or `CreateAccountScreen` ("Create one").

- **`diet_preferences_screen.dart`** — Two-step diet + allergy picker, reused for both first-time onboarding and later editing, now via a required `isOnboarding` constructor flag (a real back-stack bug, found during a back-button audit: finishing always did `pushReplacement(MainScreen)` regardless of context, which for onboarding left SignInScreen/CreateAccountScreen still reachable via system back from a newly-registered signed-in user's Home tab, and for editing pushed a *second* MainScreen on top of Profile instead of just returning to the existing one. Onboarding now uses `pushAndRemoveUntil` to fully clear the stack; editing just pops back with a `true` result, and `ProfileScreen._editPreferences()` reloads on that result. Editing mode also gained a proper header back button on step 1 — previously the only back control was the step-2-to-step-1 wizard chevron, so there was no way to cancel out of editing at all without the OS back gesture). Loads existing selections via `AuthService.getDietPreferences()`/`getAllergies()` on open. Calls `AuthService.saveDietPreferences()`/`saveAllergies()`.

### Legal
- **`terms_screen.dart`**, **`privacy_screen.dart`** — Static content, `StatelessWidget`s, no service calls. Reached from Settings or Create Account's inline links.

### Main Tabs
- **`home_screen.dart`** — Dashboard: pantry/expiring/recipe-match stat cards, quick actions (AI Scan/Add Item/Waste Control), an expiry alert card, recent ingredients, top 3 recipe picks. The insight banner is three-state, in priority order: any expired items → red "CLEAN UP" banner (tap-through to Expiry Monitor); else anything expiring today/soon → amber "AI INSIGHT" rescue banner (most urgent ingredient + a real rescue-recipe count derived by cross-referencing `getExpiryStatus()` against `getRecipesDetailed()`); else the green "Your pantry is fresh!" message. Calls `ApiService.getRecipesDetailed()`, `getAiRecommendation()`. Navigates to `RecipeDetailScreen`.

Calls `ApiService.getInventory()`, `AuthService.getName/Email/CreatedAt/DietPreferences/Allergies()`, `CookedHistoryStore`. Navigates to `SettingsScreen`, `DietPreferencesScreen`, `StatisticsScreen`, `WasteControlScreen`, `CloudSyncScreen`, `SignInScreen` (after logout).

## Frontend Tests — `frontend/fridge2table_app/test/`

### `local_recipe_matcher_test.dart`
The first automated test in the repo (previously `test/` was present but empty — see `docs/PROJECT_OVERVIEW.md` §6). Verifies `LocalRecipeMatcher` stays in lockstep with the backend's own `_matched_recipes`/`_expiry_map`:
- The bundled `assets/data/recipes_full.json` is byte-identical to `backend/data/recipes_full.json`, and has all 302 recipes with unique ids.
- Four real pantries (a small pantry exercising the relaxed match-count threshold, a larger one exercising the standard threshold, one exercising synonym/pluralization normalization, and one covering a different cuisine) each return real matches.
- A separate test dumps full match + expiry-annotation output to a scratch JSON file, meant to be diffed against the equivalent output from calling the backend's `_matched_recipes`/`_expiry_map` directly in a throwaway Python script (bypassing HTTP/DB entirely) for the identical pantries — this is how the two were confirmed to produce **byte-identical results** (same recipe names, same `match_score`, same `matched_ingredients`, same `expired_ingredients`/`expiring_ingredients`) for every test pantry, not just "similar" ones. That comparison surfaced one real, fixed discrepancy: neither the backend's nor the Dart matcher's sort had a secondary tie-break key, so which specific recipes landed in the last few slots of a 25-result list was arbitrary whenever several tied on `match_score` right at the cutoff (Python/Dart `Set` iteration order isn't stable across implementations or even across process runs). Both sides now sort by `(match_score desc, name asc)`, making results fully deterministic and guaranteed identical between online and offline for the same pantry.

Run: `flutter test test/local_recipe_matcher_test.dart` (from `frontend/fridge2table_app/`).
